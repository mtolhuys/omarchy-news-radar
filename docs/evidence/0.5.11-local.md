# 0.5.11 Core reading-durability evidence

Status: local candidate under verification. Complete this record with the exact public commit, GitHub CI, Forge deployment of the retention floor, the public-install scenario, and the release tag before claiming release completion.

## Defect

A dismissed Omarchy News story reappeared as unread, repeatedly, for as long as the story stayed inside the RSS window.

Four shipped behaviours combined:

1. The rolling 500-event ledger is dominated by marketplace releases. The public edition fetched at `2026-09-22T22:40:06Z` carried 480 `plugin-released` rows against 5 `omarchy-news` rows; its oldest surviving protected row was dated `2026-09-11`, an eleven-day news window.
2. `diff_news` deliberately re-emits every RSS item inside the rolling window on every collect, not only newly observed ones, so an eviction can rematerialize Core stories.
3. Event identity is deterministic, so the rematerialized story returns under the same ID.
4. `set_events_read` pruned the override map to the current reading feed on every reading mutation.

Plugin decisions survived eviction only because the `setup-news` companion carries `plugin-released` and `plugin-retired`; `SETUP_EVENT_TYPES` excludes official news, so news dismissals had no second carrier and were deleted outright.

Measured on the reporting desktop before the fix: 30 items in the live RSS, 7 in the local ledger, and 23 with neither a ledger row nor a read override despite having been read. All 7 ledger rows recomputed to exactly the IDs already marked read, so identity was stable and the loss was the override, not event churn.

## Reproduction

A copy of the real desktop state in a temporary XDG root, with one Core story removed from the cached feed and one unrelated story read, moved that story's override from `True` to absent in a single mutation. `readThrough` was `2026-09-01T00:10:16Z`, so the story was not covered by the baseline either and returned unread.

## Repair

- `set_events_read` retains overrides whose events are absent from the current edition. `_bound_read_overrides` keeps the map inside the existing `MAX_READ_OVERRIDES` cap: entries for events in the current reading feed are always kept, and unreachable entries are dropped only under cap pressure, oldest event ID first for determinism.
- `retain_events` reserves `CORE_RETENTION_FLOOR` (20 `omarchy-news`, 3 `omarchy-released`) before the remaining protected lane competes for the 500-event bound. Under a synthetic 900-release flood the floor keeps 20 news rows spanning 19 days where the previous behaviour kept 5 across 11 days, while `plugin-released` retention stays above 400 rows and D066 mandatory additions still survive.

## Compatibility

- Local state schema remains **v13**; no migration runs and no existing reading decision changes on upgrade. The override map keeps its 6,000-entry bound and canonical sorted serialization.
- Feed schema remains v2; insights and setup-news remain v1; helper protocol remains v1.
- No new network origin, dependency, permission, daemon, or configuration mutation. Front Page composition, significance, curation, event identity, timestamps, and ordering are unchanged.

## Deployment split

The two halves ship by different routes:

- The override repair is client-side and reaches desktops through the plugin release and marketplace verification.
- The Core retention floor is collector-side and only changes the public edition once Forge's `NEWS_RADAR_PATH` checkout carries this commit and a scheduled `news-radar:publish` runs.

Until Forge carries it, public editions keep the eleven-day news window; the override repair alone still stops dismissals being destroyed.
