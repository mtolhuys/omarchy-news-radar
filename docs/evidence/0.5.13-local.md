# 0.5.13 fetch-outside-the-plugin evidence

Status: released candidate under marketplace verification.

## Why

The marketplace blocker on issue #6193 (HANCORE-linux, 2026-09-22T23:47:23Z) read: `radar/plugin_update.py` can fetch and install a newer mutable remote HEAD outside this exact reviewed snapshot. 0.5.12 removed every install path. It still fetched the remote tip into the installed plugin's own `.git` to read the newer manifest version. That never installed or ran anything, but the finding names fetching as well as installing, so 0.5.13 removes the write too.

## Repair (D074, refined)

- `inspect_update` reads the origin address with `git remote get-url origin` and refuses anything that is not a plain repository address. The address is now a git argument: a leading `-` would be read as an option, and `ext::`/`fd::` transports run commands.
- `_fetch_remote_tip` fetches only the remote tip (`--depth=1`, 30-second limit, `GIT_TERMINAL_PROMPT=0`) into a throwaway bare repository under a `tempfile.TemporaryDirectory`, and the fetched manifest is read there. The fetch no longer inherits the installed checkout's local configuration or hooks.
- Inside the installed plugin the check runs only `rev-parse`, `cat-file`, `show` and `remote get-url`.
- `scripts/validate_repo.py` fails if the helper fetches through the plugin checkout or stops using a temporary directory.
- A shallow fetch is about 1.4 MB against the 37 MB full history, for both a local origin and `https://github.com/mtolhuys/omarchy-news-radar`.

## Verification record

- `make test`: 352 tests passed (the update suite grew from 8 to 10).
- A byte-for-byte snapshot of every file in the installed plugin, including `.git`, is identical before and after the check, with no `FETCH_HEAD` created, for clean and divergent checkouts.
- Option-shaped, `ext::`, `fd::` and newline-bearing origin addresses written directly into `.git/config` are refused as `blocked` before any fetch, and none of them executes.
- Mutation check: restoring the 0.5.12 `radar/plugin_update.py` fails `test_the_remote_is_fetched_outside_the_installed_plugin`, `test_a_newer_release_is_reported_and_never_installed` and `test_can_apply_is_false_for_every_checkout_shape`, each reporting that `fetch` ran inside the installed plugin. Run against a planted `https://example.com` origin, the 0.5.12 check also hung with no timeout; 0.5.13 bounds the fetch at 30 seconds and disables credential prompts.
- `make validate`: all checks passed, including ShellCheck for 17 scripts.
- `tests/lab/update-notice.sh`: passed in the disposable Omarchy 4.0.3 guest, run `omarchy-iso/test-runs/omarchy-4.0.3/runs/20260923-094825`, 6 screenshots. The origin's default branch advanced to an unverified `99.0.0` commit and Radar showed the marketplace notice. The installed plugin's repository fingerprint — `FETCH_HEAD` presence and hash, loose and packed object counts, and every ref — was identical before and after (`no-FETCH_HEAD`, 320 objects). The installed `HEAD`, version and worktree were unchanged, `update-apply` was refused, and the journal showed no updater run.

## Compatibility

- Helper protocol remains v1; the `update-status` response shape is unchanged.
- Local state schema remains v13; feed schema remains v2; insights and setup-news remain v1.
- No new network origin, dependency, permission or daemon. The check contacts the same origin as before.
